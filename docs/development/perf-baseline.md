## 1. Reproducing this

```bash
# Generate the corpus and prove hledger accepts it (strict mode).
nix develop -c ./scripts/gen-perf-journals.sh 5000 50000 200000
# or: just perf-corpus 5000 50000 200000

# Run every bench at every size and record a named baseline.
nix develop -c just bench-save phase6

# After a change, re-run and get a per-bench delta.
nix develop -c just bench-compare phase6
```

Default `cargo bench` covers **5k and 50k only**; adding 200k roughly doubles the
run. Opt in with the `LEDGELINE_BENCH_SIZES` environment variable, which takes a
comma-separated list of transaction counts:

```bash
LEDGELINE_BENCH_SIZES=5000,50000,200000 nix develop -c cargo bench -p ledgeline-core
LEDGELINE_BENCH_SIZES=200000 nix develop -c cargo bench -p ledgeline-core -- 'reports/net_worth'
```

Wall-clock for the run that produced this document (all three sizes,
**81 benchmarks**): **~14 minutes**, of which roughly 6 were the 5k pass. A
default two-size run is about 8 minutes.

### Peak RSS

Criterion measures time, not memory, and PERF-1 is a memory finding. Use the
`load_rss` example, which builds exactly what `Snapshot::from_journal` holds and
then keeps it alive until process exit:

```bash
nix develop -c just perf-rss 200000
# or by hand:
nix develop -c cargo build --release -p ledgeline-core --example load_rss
/usr/bin/time -l ./target/release/examples/load_rss 200000 --stage snapshot
```

`--stage` is one of `text | parse | clone | value | snapshot | bytes`. The first
five are nested, so subtracting consecutive peaks attributes the growth; `bytes`
is off to the side and models the PERF-1 target state (journal + serialized bytes,
no `Value` tree, no journal clone).

On macOS `/usr/bin/time -l` reports `maximum resident set size` in **bytes**; on
Linux use `/usr/bin/time -v`, which reports KB.

## 2. The corpus

Generated by `crates/ledgeline-core/benches/corpus.rs`, cached in `target/perf/`
(gitignored — 26 MB of synthetic journal does not belong in git).

**Determinism.** `generate(n)` is a pure function of `n`. The only entropy source
is a SplitMix64 seeded from a compile-time constant and advanced in a fixed
order; there is no clock, no environment read, no `HashMap` iteration, no `f64`
anywhere in the money or date math. Verified: deleting and regenerating all three
journals reproduces identical SHA-256 digests.

```
65ba2490fe8ac04e2cd2f08d11b95eca465cd96f22bd866d00c8c5e943acee0e  synthetic-v1-200000.journal
f411fd8d8b8ce7b9a73a4e7f487cdb2efdd7401c984e65473406c8506456147e  synthetic-v1-5000.journal
7cb9a3cb7847c13ac80e6cf46da6a2483d91b221253612e386b756c5ff2dacc6  synthetic-v1-50000.journal
```

The filename carries `CORPUS_VERSION`, so any change to the emitted shape must
bump it and cannot be masked by a stale cache.

**Validity.** All three pass `hledger -f <file> check -s` — strict mode, i.e.
every transaction balances, every balance assertion evaluates, every account and
commodity is declared, and every date is a real calendar date. Phase 2 added the
same strictness to the engine, and the generator's balance assertions are
computed from an exact `i64`-cents running balance rather than from rounded
display text.

| | Generated | CLEANUP.md's stated shape |
|---|---|---|
| Declared accounts | 300 | 300 |
| Accounts actually used | 248 | 243 |
| Commodities | 5 (`$`, `EUR`, `AAPL`, `VTI`, `GLD`) | 5 |
| `P` directives | 1,488 | 1,488 |
| Date span | 1996-01-01 → 2025-12-31 (10,958 days) | 30 years |
| Postings / txn | 2.20 (443,440 at 200k) | ~2.1 (420k at 200k) |
| Cost-annotated amounts (`@`/`@@`) | 18,203 at 200k | ~18,530 implied |
| Total `PriceDirective`s after inference | 19,691 at 200k | 20,018 |
| Source size 5k / 50k / 200k | 0.70 / 6.58 / 26.18 MB | 0.74 / 7.0 / 27.7 MB |

Also included, because the engine paths under test need them: `~ monthly` and
`~ yearly` periodic rules (so `budget_report` has goals), unbalanced `(a)` and
balanced-virtual `[a]`/`[b]` postings, transaction and posting comments, `type:`
tags on roots and cash accounts, all three statuses, elided amounts, digit-grouped
`$1,234.56` and comma-decimal `1.234,56 EUR` styles.

**Where the shape differs and why it matters.** The corpus is ~5% smaller per
transaction than CLEANUP.md's and carries ~5% more postings per transaction. Both
are small, and the timings below track the document closely enough that the
journal shape is not the explanation for any of the discrepancies in §4.

### Two claims the baseline actively contradicts

1. **PERF-5f (`roll_up` clones the accumulator) is a rounding error, not a
   finding.** `aggregate/roll_up` is **flat in journal size**: 131 µs at 5k,
   133 µs at 50k, 144 µs at 200k. Its input is `account_totals`' output, whose
   size is bounded by the *account count* (248), not by the transaction count. It
   is called once per bucket inside `net_worth`, so at 60 buckets the entire
   theoretical win is ~8.6 ms out of 2,508 ms — **0.3%**. The clone-per-addition
   is real and worth fixing on style grounds, but do not budget optimization time
   against it and do not expect a measurable delta.

2. **`net_worth` is ~95% `account_totals` re-scans**, which is exactly what
   PERF-5's single-pass rewrite targets. `account_totals` alone is 43.8 ms at
   200k; `net_worth/count_12` is 552 ms ≈ 12 × 43.8 ms + 26 ms. This is the
   strongest quantitative support in the whole phase, and it says the fix should
   land close to the 50 ms estimate. The three *other* wastes PERF-5 lists inside
   the loop (`roll_up`, the double `at_depth`, `remap_account`) together account
   for the remaining ~5%.

Two smaller calibrations for whoever picks up PERF-5e:
`accounts/declared_types` is 2.9 µs, so "rebuilt on every HTTP request" is true
but costs microseconds; and `resolve_account_type_sweep` is 26.8 ms per full
posting sweep at 200k (60 ns/call), so memoizing it is worth tens of
milliseconds per report, not hundreds.

## 5. How to compare after a change

```bash
# 1. Confirm you are diffing against the same corpus.
shasum -a 256 target/perf/*.journal      # must match §2

# 2. Re-run and let criterion do the comparison.
nix develop -c just bench-compare phase6
```

Criterion prints `change: [-x% -y% -z%] (p = …)` per bench and labels each
`Improved` / `Regressed` / `No change`. With `sample_size = 10` on the heavy
groups it will not resolve anything under about 5%; every Phase 6 finding claims
3–10×, so that is ample. Do not "improve" a number by regenerating the corpus:
bumping `CORPUS_VERSION` invalidates this baseline entirely and the whole table
above has to be re-measured.

The four benchmarks to gate on, because they are what the user feels:

| Bench | Baseline (200k) | Target after the fix |
|---|---|---|
| `wire/snapshot_from_journal` | 1,696 ms | ≤ 700 ms (PERF-1) |
| `reports/net_worth/count_60` | 2,508 ms | ≤ 200 ms, and within 2× of `count_12` (PERF-5) |
| `holdings/holdings_series_12` | 1,567 ms | ≤ 300 ms (PERF-5b) |
| `reports/insights` | 1,197 ms | ≤ 400 ms (PERF-5c) |

Plus one pair that must *converge* rather than shrink:
`prices/lookup_early_date` (8.27 µs) and `prices/lookup_late_date` (23.2 ns)
should end within an order of magnitude of each other once `latest` uses
`partition_point`.

And peak RSS at 200k: **3,563 MB → the `bytes` stage's 1,478 MB** is the
mechanical floor for PERF-1 as currently written. Note that 1,478 MB is itself
inflated by the intermediate `Vec<WireTransaction>` that `journal_to_transactions`
materializes before serialization — serializing streaming, or straight from the
`Journal`, would take it lower still.

## 6. Known gaps

- **No `crates/ledgeline-server` benches.** CLEANUP.md asks for
  `benches/snapshot.rs` with `snapshot/from_journal` and
  `snapshot/serve_transactions`. `Snapshot` is `pub(crate)`, and the server crate
  was out of this agent's scope, so `wire/snapshot_from_journal` in the core
  bench replicates `Snapshot::from_journal`'s body instead. **It is a hand-kept
  copy**: if `Snapshot::from_journal` gains or loses a payload, update
  `snapshot_payloads()` in `benches/engine.rs` to match, or the number silently
  stops meaning what it says.
- **No HTTP-level benches**, so PERF-2 (ETag/compression/windowing), PERF-3
  (`spawn_blocking` under concurrency) and PERF-4 (watcher debounce) have no
  numbers here at all. They need a server-side harness.
- **No `parse/includes_200k`.** CLEANUP.md asks for it to show that `include`
  splitting costs nothing; the generator emits a single file. Adding it means
  teaching the generator to shard into `include`d files.
- **No CI wiring.** `nix build .#clippy` runs `--all-targets`, so the benches and
  examples are *compiled* in CI and cannot rot (verified: `.#clippy`, `.#fmt` and
  `.#tests` all pass with these files present). Nothing *runs* them or compares
  baselines, though — a shared runner would be too noisy for the ~5% resolution
  above without pinning. Note that Nix flakes only see git-tracked files, so
  `nix build .#clippy` fails with "can't find bench `engine`" until
  `crates/ledgeline-core/benches/` is committed.
- **`cargo-llvm-cov` is still absent** from `flake.nix` (out of scope here), so
  every coverage claim in CLEANUP.md remains read-derived.

## 7. The v2 large-repo corpus (200 commodities, 75 accounts)

Added 2026-08-31. **Everything above is v1 and is unchanged**: `generate(n)` is
frozen on the `V1` shape, and the three SHA-256s in §2 were re-verified against
the parameterized generator before and after this section was written. If a v1
digest ever moves, §3 is void — do not reconcile it, regenerate it.

### 7.1 Why a second corpus

v1 has **five** commodities, so every per-commodity cost in the engine is
multiplied by five and disappears into the noise. Several findings are quadratic
or worse in the commodity count and are therefore invisible on it. v2 is the
fixture from the original ask — 10k transactions a year for 15 years, ~200
commodities, 75 accounts — and the account and commodity budgets are in
deliberate tension: one position account per (broker × symbol) would mint 400
accounts, so **25 commodities share each brokerage account**. That is the only
way to get a `MixedAmount` (`BTreeMap<Commodity, Dec>`) that is 25 entries deep
per account rather than 1.

`v2fx` is the same journal with a **mesh** price graph instead of a `$`-star.
Three guards in the engine only disarm on a mesh, and a star-only corpus would
have measured none of them:

| Guard | What disarms it in `v2fx` |
|---|---|
| `value_at`'s direct-lookup fast path (`prices.rs:622`) | ~59 of the 200 symbols are quoted in EUR or GBP, so `lookup_in` misses and `graph_at` runs |
| `PriceGraph` single-hop chains | GBP is quoted in EUR and CHF in GBP, so reaching `$` is a 2- and 3-hop chain |
| `choose_base`'s "fewer than 2 candidates" short-circuit (`engine.rs:1298`) | three price targets (`$`, EUR, GBP) **and** one deliberately unpriceable symbol, so no candidate ever prices everything and every one is scanned |

**The same fixes are worth 1–3% on v1 at 200k and 6.7× on v2.** That is the

| | before | after |
|---|---|---|
| v2 | 902.4 / 274.8 = **3.28×** | 134.2 / 124.7 = **1.08×** |
| v2fx | 990.8 / 343.4 = **2.89×** | 209.2 / 180.3 = **1.16×** |

**not** because `pool_snapshots` had started splitting the replay, but because
the per-point pricing scan dominated and hid the fact that it had not. On v1 the
same ratio reads ~1× either way, so v1 could not have told the two apart.

### 7.4 What v2 answers about the predictions

The four paths TODO.md predicted would fall over, with what was actually
measured:

1. **`latest_directive_price` — holds up.** 123 ms per `compute_holdings` at
   150k/C=200/36,180 directives is 0.82 µs per transaction, against v1's 0.97 µs
   at 200k. The 24× directive count and 40× commodity count cost nothing, which
   is what an `O(log P)` index is supposed to look like. **One residual**: the
   walk returns early only on a directive priced in the base, so a symbol that is
   *never* priced in the base scans its whole in-effect prefix. `v2fx` has 59
   such symbols and pays 0.60 ms per series point against v2's 0.20 ms — a 3×
   per-point cost that is entirely this. Not fixed; measured.
2. **`value_at`'s per-call `PriceGraph` rebuild — NOT reproduced.**
   `reports/balance_sheet` is 28.7 ms on the star and 29.2 ms on the mesh (+2%);
   `net_worth`, `insights` and `income_statement` are all within 1%. The graph is
   built lazily and at most once per `value_at` call, and `reachable`'s
   `O(V·E)` only bites when many nodes are reachable — this mesh is a
   star-of-stars whose chains are 2–3 hops with a handful of reachable nodes, so
   `shortest_path` never enumerates anything. **A denser graph is what that
   finding needs**; `v2fx` is a fair mesh but not a dense one, and that is a
   limitation of this fixture rather than evidence against the finding.
3. **`choose_base` → `coverage` — confirmed, and it is the mesh's main cost.**
   Everything mesh-related lands in `holdings`, not in the reports: +39% on
   `compute_holdings`, +45%/+56% on the 12- and 60-point series. v2 has one
   candidate and short-circuits; v2fx has three and an unpriceable symbol, so no
   candidate ever prices everything and all three are scanned.
4. **`pool_snapshots` replay splitting — did NOT happen; the PERF-5b fix
   survives C=200.** `series_60 / series_12` is 1.08× (v2) and 1.16× (v2fx). A
   split into `min(D, 2A)` replays would have put `series_60` near 60 ×
   `compute_holdings` ≈ 7.4 s; it is 134 ms. This was the regression most likely
   to hide behind a passing v1 gate, and it is not there.

Two smaller results worth recording. `aggregate/roll_up` is 130 µs on v2 against
65 µs on v1 — the only place the 25-commodities-per-account `MixedAmount` shows
up as a clean 2×, and it is still microseconds. And `prices/lookup_early_date`
(28.9 ns) versus `lookup_late_date` (11.6 ns) stay within 2.5× of each other at
36,180 directives, so PERF-5d's convergence holds at 24× the directive count.

### 7.5 Not measured

- **Peak RSS on v2.** `examples/load_rss` takes a transaction count, not a
  shape.
- **A dense price graph.** See finding 2 above — the `PriceGraph`/`shortest_path`
  cost needs a many-to-many FX graph, which would be a third shape.
- **`/api/insights`'s 7 `PriceDb::build`s.** `prices/PriceDb_build` is 5.70 ms on
  v2 against 1.69 ms on v1 at 200k, so seven of them is ~40 ms per request, but
  nothing here counts the calls.
